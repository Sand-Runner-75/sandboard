# Read-only data layer

How the app reads private project data from GitHub, and what it refuses to do. The code is in `src/sb-core.js`, `src/sb-readers.js` and `src/sb-render.js`. The workspace views built on it are described in [WORKSPACE.md](WORKSPACE.md).

## Access

- The owner makes a fine-grained GitHub token limited to the mapped repositories, with read-only **Contents** and **Metadata** (and **Checks** for check runs, **Pull requests** for a task's review cycle and pull request reviews, **Issues** for the issue list, and **Actions** for workflow runs). It is pasted into a password field and kept only inside one session object in memory, where nothing outside `src/sb-core.js` can read it (only the module's own client turns a live run into the request header): never in browser storage, cookies, the URL, history, logs or error text. The field is cleared at once.
- **Forget token**, leaving the page (`pagehide`, including into the back/forward cache), a page restored from that cache (`pageshow`) and a `401` reply all end the session: pending requests are aborted, the token is dropped and everything read with it is cleared. Reload or a new tab starts signed out.
- The page refuses to run inside a frame.

## Requests

- One client sends every request, always `GET` to `https://api.github.com`, with `credentials: "omit"`, `cache: "no-store"`, `referrerPolicy: "no-referrer"` and `redirect: "error"`. It has no way to send anything else.
- Paths must match an allowlist (`/user`, the token's own list of repositories (pages 1 to 9), a repository, a commit, a file at a full commit SHA, a commit's check runs, a repository's pull request list, the comments on one pull request, a repository's languages, the latest 30 commits from a full commit SHA, a repository's latest 50 issue and pull request comments, a page of 100 commits behind a full commit SHA (any page from 1 up), a repository's branches and tags (pages 1 to 3), how one full commit SHA compares with another, a repository's pull requests or issues by state (open, closed or all; pages 1 to 9), one pull request's reviews (pages 1 to 3), a repository's workflow runs and releases (pages 1 to 9), and the whole file tree at a full commit SHA), and, for the Atlas's **Your account** only after it is asked for, the signed-in login's public profile (`/users/<login>`) and its public events (`/users/<login>/events/public`, pages 1 to 3), and, only after they are asked for too, its starred repositories (`/users/<login>/starred`) and public gists (`/users/<login>/gists`), pages 1 to 3 each. No other account-wide path (private or received events, notifications, searches, the contribution calendar) is allowed. Anything else is refused before any network call.
- Each run has a context. The session checks it before each request and after each reply, body read and hash, so a reply from a forgotten session or an older run never appears. A new run aborts the old one.
- Tests (`tests/test_app_rules.py`) fail if any browser code uses another network API, an HTTP method other than `GET`, a second network call site, browser storage, HTML parsing or code evaluation, or console logging.
- One exception to "nothing stored", by the owner's choice: the order of projects in the left tree is kept in this browser's local storage under `sandboard.projectOrder`, as a list of project IDs. It holds nothing read from GitHub and never the token; the rules test allows that one key, read and written only in `src/app.js`. If storage is off or full, the order holds for the visit.

## Pinning

Every view reads one repository at one commit: a branch or tag (the default branch when none is named) is resolved to its commit once, and every file of that view is read at that SHA. A file counts only if its bytes match GitHub's git blob hash.

## Result states

Every reader returns `{state, data, source: {repo, ref, commit, path}, schema, error}`. `state` is one of `loading`, `current`, `empty`, `no-match`, `missing`, `denied`, `rate-limited`, `invalid`, `stale`, `unavailable`, `partial`, `failed`. Only `current`, `empty`, `no-match` and `partial` carry data; `partial` also gives `coverage`. No state is ever shown as zero or success. HTTP `404` is `missing`, `403` is `denied` unless it is a rate limit, `403` with an exhausted limit or `Retry-After`, and `429`, are `rate-limited`, anything else, and a network failure or a reply body that cannot be read, is `failed`. A network failure that arrives after Forget or a newer run is dropped like any late reply. Each reader returns its own state, so one failing repository stops only the reads that depend on it; the other workspaces are still read (`SB.readWorkspace`).

## Workspace list

Read from the private plan repository named at sign-in, file `sandboard.workspaces.json`, at the pinned commit. Missing or invalid: no workspaces are shown, with the reason. Nothing is guessed from repository names. When sign-in gives only an owner, or nothing, the plan repository is found instead: every repository the token can read (of that owner, up to 50, five at a time) is checked for that file at its default branch, and it is used only when exactly one has it and the search is complete: the token's list was read whole, it was under the limit, and every repository answered (a repository that is not found or has no commits has no list; one that is denied, limited or fails is unchecked). Several, none, an incomplete search or a token list that cannot be read: nothing is loaded, and the page says which, naming what it found and what it could not check. Refresh searches again.


```json
{
  "schema": "sandboard.workspaces/1",
  "workspaces": [
    {
      "id": "garden", "label": "Example Garden Planner", "kind": "project",
      "plan": { "repo": "owner/plan-repo", "ref": null,
                "files": { "progress": "plan/progress.json", "producer": "tools/progress.py",
                           "table": "plan/tasks.md", "record": "plan/record.md" } },
      "code": [ { "repo": "owner/code-repo", "ref": null, "role": "app" } ]
    }
  ],
  "found": { "files": { "progress": "plan/progress.json", "producer": "tools/progress.py",
                        "table": "plan/tasks.md", "record": "plan/record.md" } }
}
```

`kind` is `project`, `kit` (a reusable template, not a live project) or `standalone` (code only); `plan` may be `null` when `code` is not empty; `ref` `null` means the default branch. The four plan file paths come from this private file, so the public code names no private file.

`files` may also name `brief`, `handover` and `crossref` (the task's cross-reference index): path templates with exactly one `{id}`, such as `"notes/{id}-brief.md"`. A task's brief, handover or cross-reference file is the template with the task's ID (letters, digits, `.`, `_`, `-`), read at the pinned plan commit (`SB.readTaskFile`): `current` with its text, `empty`, `missing` when the task has none, `invalid` when it is not UTF-8 or the ID or template is not valid (no request is made then), or the read's own failure state. Without a template the view says the workspace names no such file.

### Repositories found through the token

After the list, the token's own list of repositories is read (`/user/repos`, 100 a page, up to 9 pages; only each `full_name` is kept, `SB.readAccountRepos`). Every repository on it that the workspace list does not name as a plan or code repository (compared without case) is shown too, marked **found**, after the listed ones and in name order. The optional `found.files` (the same fields and rules as a plan's `files`) is the layout a found repository is read with as a plan; when its task table is missing at the pinned commit, or the list gives no `found`, it is read as code only. A found plan with no progress file shows its tasks without progress figures (**unavailable**, never 0%). Naming a repository in the list still gives it a label, a kind and its code repositories. A list GitHub does not give (refused, failed or malformed) adds nothing and is said on All repositories; nine full pages are shown as **partial**.

## Plan table

Every Markdown table whose first header cell is `ID`, in order, with the heading above it as its section. Each row's fields stay text exactly as written. Rows with the wrong number of cells, no ID or a repeated ID are kept and marked invalid. Nothing is added up.

## Stored progress (`sandboard.progress/1`)

The plan's own producer stores its result in the progress file. It is read at the pinned commit and checked field by field: `schema`, `ok: true`, counts, the producer and its inputs, which must include the table and the record at the paths named in the workspace list, all with 40-hex blob SHAs (a producer that reads more files names each further input with its own path and hash, up to ten in all), all four scopes and every phase with every figure: hours (`estimated_h`, `completed_h`, `remaining_h`) are non-negative numbers; `progress_pct` (at most 100), `tbe_rows`, `proposed_rows`, `provisional_rows` and `rows` are non-negative whole numbers; `verified` is true or false; phase IDs (`P<n>`) are unique and in order; each phase's `status_counts` has exactly the six statuses Not Started, In Progress, Blocked, Ready for Review, Done and Removed, each a non-negative whole number. Then the producer and every input are read at the same commit:

- all three blob SHAs match: **current**, shown with its source commit and schema;
- any differs or cannot be read: **stale**, with the reason;
- no progress file: **unavailable**; the progress file itself denied, rate-limited or failed: that state;
- not JSON, wrong schema, `ok` not `true` or any field wrong: **invalid**.

Two blocks are additive: absent means this producer does not supply them, and present means every field is checked, or the whole result is invalid.

- `stages`: a non-empty list of `{id, name, phases, gate}` with the same figures as a phase. Each named phase must be in `phases`, in at most one stage; `gate` is a name or `null`. The view shows stage figures only from here and never adds phases up.
- `approved_results`: `{id, approval, files, rejected}` for each task whose owner approval the producer has recorded: `files` are repository-root paths (plain path segments only), `rejected` are link targets the producer refused (outside the repository, a URL, a query or fragment), shown as text and never followed. Owner approval is shown only from here; a Done status, a review verdict or passing checks never stand in for it.

Figures are shown exactly as stored, never recalculated. "Current" means "matches the pinned commit"; there is no time limit, and refresh is manual. A project refresh reads one workspace again with the same reads as sign-in (its plan and code repositories at their branches now) in the current run, and drops only that project's live reads and unfinished task-file reads; it never reads the workspace list or the token's list of repositories.

## Check runs

Read for a pinned commit, 100 per page, up to five pages. A `403` or `404` (the token has no **Checks: read**, or it is not proved) is **unavailable**, never "no checks". **Empty** only when GitHub reports none. Fewer runs read than GitHub reports, even none, is **partial**, with the coverage shown. A negative or changing total, or more runs than the total, is **invalid**.

## Pull requests and comments

Read live, not at a pinned commit, only when a task's review cycle is opened. The list is `pulls?state=all`, 100 per page, up to three pages; a third full page makes it **partial**. Each pull request must have a whole number, a title, `open` or `closed`, a full head commit, and, when given, a merge time, a full merge commit and a text body, or the list is **invalid**. Comments on one pull request are read 100 per page, up to five pages, kept as text with their time; more than that is **partial**.

## Review cycle

A plan pull request belongs to a task when its title names the task's ID standing alone: `XQ02` does not match `XQ026`, and a step `XQ026.1` does not match `XQ026`. A code pull request belongs when such a plan pull request's description links it by web address, `owner/name#12`, or the code repository's own name followed by `#12` or `PR #12`. At most ten pull requests are read per task. For each one, the comments and the check runs at its head are read.

A comment counts as a review only in the handoff form: lines starting `FROM:`, `STATE:` and `HEAD:` (with `TO:`, `RESULT:`, `NEXT:` optional, and `FROM: A → TO: B` on one line accepted). Its state is shown as written, and recognised when it starts with READY FOR REVIEW, CHANGES REQUESTED, READY FOR RECHECK, REVIEW PASSED, BLOCKED or OWNER DECISION. Its head is the first full 40-character commit on the `HEAD:` line; it is labelled for the head, for an older commit, or as naming no full commit. A handoff is superseded when the same sender posts a later one. Other comments are only counted. Owner approval still comes only from `approved_results`; a review verdict, a passing check or a merge is never shown as one.

## Repository overview

Pinning also keeps what GitHub's repository reply says, field by field (`meta`): description, visibility, fork, archived, main language, topics, licence and main language (each `none` when GitHub says there is none), default branch, stars, forks, open issues, size, created, last push and homepage. A field that is missing or not in the expected form is `null`, shown as "Not given by GitHub", never as zero or a guess. These are read only for repositories the workspace list maps (or the owner opens by name for the visit).

Three live reads, made when a view needs them and read again on refresh:

- **Languages** (`/languages`): bytes per language, largest first; `empty` when GitHub counted none; any entry that is not a name with a whole non-negative number makes it **invalid**.
- **Commits** (`/commits?sha=<pinned commit>&per_page=30`): the latest 30 reachable from the pinned commit, each with its SHA, first message line, committer time and parent count; 30 back is **partial**.
- **Comments** (`/issues/comments?sort=created&direction=desc&per_page=50`): the latest 50 on the repository's issues and pull requests, each with the number it was posted on; 50 back is **partial**; a `403` or `404` is **unavailable** (the token lacks **Pull requests: read**), never "no comments".

The activity feed also reads one page of the pull request list (100). Only handoff comments are shown, read as in the review cycle. Sums over repositories (stars, forks, issues, code bytes) are added only over the repositories that gave them, with that count shown. Counts by visibility and by original or fork say over how many repositories they are too, and an unknown value is its own filter choice ("Not given by GitHub"). A repository's feed is read at the commit its project pinned, so the same repository at two refs has two feeds. Events with no readable time are counted and said, never placed in order, and a feed of only such events does not read as empty. None of these reads or figures feeds progress.

## History

A repository's history is read from the commit its project pinned, 100 commits a page, with no last page: the first page, then each next one when the list is scrolled to its end or the owner asks. A full page says older commits may exist; a shorter one is the start of the history. Each commit keeps its ID, title (first line), commit time, parents' IDs and the GitHub login of its author when GitHub links one; the author's name and email address in the commit are never kept. Branches and tags are read as GitHub lists them now (up to 300 each, partial when full), each with the commit it points at and, for a branch, whether it is protected (not given when GitHub does not say). A comparison reads only GitHub's ahead and behind counts, its state and the merge base (`compare/<read commit>...<branch head>?per_page=1`); a compared branch's own commits are read page by page behind its head, each next page only while a commit they reach is not read yet, and stop at the history already read or the merge base. Commits per week and by day, and contributors, are counted over the commits read only, and only the weeks and days shown (12 and 182) are built, however far apart the commit dates are; they are GitHub activity and never feed progress. No checkout, branch, reset, merge or statistics endpoint is used.

## Atlas branch graph

The Atlas branch graph reads nothing of its own: it uses the history's branch and tag lists, the history pages behind each drawn branch's head (`commits?sha=<head>&per_page=100&page=n`, the same key as a compared branch's lane) and the first page of all pull requests (and of the open ones when that page is full), so a refresh or a one-project refresh drops them the same way. A pull request names a branch only when its head is in the same repository. A commit's files come from `commits/<sha>`, read once per commit when the pointer rests on its dot. Which branches are drawn, which pages are still wanted and where everything goes are worked out in `src/sb-atlas-graph.js` as plain data; the view draws it with DOM calls. Nothing is written or kept beyond the visit.

## Atlas code tree

The Atlas's **Your account** reads nothing until **Show your public profile and activity** is pressed. Then it reads who the token reads as (`/user`, login only), that login's public profile (`/users/<login>`: login, type, name, bio, location, company and website, each kept as short text, follower and following counts, the creation time, and the profile page only when GitHub gives an https address whose path is that login, as for repositories; the website is never linked) and its public events, 100 a page and at most 3 pages, since GitHub keeps at most 300 from the last 90 days. An event keeps only its type, time, repository name, a push's commit count (when GitHub gives one), the action word and the kind of ref created or deleted; never a message, title, body or actor. An event not in that form is left out and counted; three full pages, or a later page that fails, are **partial** and say so. The activity calendar is the last 91 days by the viewer's local day, a push counting its commits when GitHub says how many and any other event 1; its four levels are the quarters of the active days. The contribution calendar is not read (it needs a GraphQL POST, which this client never sends), and private activity is not read. These reads belong to no repository, so a one-project refresh keeps them; a full refresh reads them again; signing out drops them and the ask. **Read again** drops only the reads that failed. **Show your starred repositories and public gists** reads, 100 a page and at most 3 pages each, the repositories the login starred (name, description and language as short text, star count, last push, archived and fork, and the page only at an https address whose path is the repository's name) and its public gists (an ID of hex digits, the description as short text, up to 50 files with name, language and size, how many more, whether GitHub cut its own list of the gist's files (then the count is said as "at least" and the list says GitHub did not list the rest), creation and update times, comment count, and the page only at an https address whose path is the gist's ID, alone or after the login); an entry not in that form is left out and counted, and three full pages, or a later page that fails, are partial and say so. File contents are never read. None of it is progress. The model is in `src/sb-atlas-account.js`.

The code tree reads nothing until Play is pressed for a repository. Then it reads, at most six at a time: the branch list (for the default branch's head), the history pages behind that head until it has the newest 150 commits, the file tree just before the oldest of them (`git/trees/<sha>?recursive=1`, files only; none when the 150 are the whole history), the first page of all pull requests, and, for each pull request merged inside the window from an agent's branch (`claude/`, `gpt/`, `codex/`, `copilot/`, and similar, at most 20), its merge commit and the first page of its commits (`pulls/<n>/commits?per_page=100&page=1`, kept by commit ID only, **partial** at 100). Last come each played commit's changed files (`commits/<sha>`). Merge commits are not played. A commit is credited to the agent whose branch brought it in, and marked as named from the branch; otherwise to its GitHub login. A commit whose files could not be read plays as changing nothing and is counted; one GitHub listed only its first 300 files of plays those and is counted apart, as are a pull request list that failed or was cut, and agent pull requests whose commits failed or were cut at 100. Only failures offer Read again, which drops just those reads. The tree draws at most 4,000 files and keeps the paths it left out, to say how many. Everything shares the keys of the history, work and code reads, so a refresh or a one-project refresh drops it. The simulation, drawing, camera and GIF recording are in `src/sb-atlas-tree.js`, and the GIF encoder is in `src/sb-gif.js`; nothing is fetched from elsewhere (coders are shown by their initial). A saved GIF or picture is handed to the browser as a download and never sent anywhere.

## Work evidence

A repository's pull requests, issues, workflow runs and releases are read live, as GitHub lists them now, not at the pinned commit: 100 a page, up to 9 pages, each only when asked. A full page says more may exist; a shorter one is the end of the list. Workflow runs are reconciled with GitHub's own total instead: the end is reached when the runs up to that page cover the total; a page short of the total is kept as short (not complete, and nothing more is read after it); one reply listing more runs than its total is invalid; and a total that changes between pages is shown as changed. A pull request keeps its number, title, state, draft, merge time, head commit and branch, base branch, author login, the logins asked to review it, the number of teams asked, and its times; a review keeps its state, the commit it was given at, the reviewer's login and its time, never its text. An issue keeps its number, title, state, close reason, author login, label names, assignee logins, comment count and times; the pull requests in GitHub's issue list are counted and left out. A run keeps its ID, workflow name, title, number, event, status and conclusion (a conclusion not known here is kept as text, never as passing), branch, head commit, actor login and times; its duration is from its start to its last update, only once completed. A release keeps its ID, tag, name, draft and pre-release flags, times, author login and each asset's name, size, download count and GitHub download address (see below), never fetched. A `403` or `404` on pull requests, reviews, issues or runs is **unavailable** with the permission it needs. The inbox reads only the first page of open pull requests and issues of each mapped repository whose own read answered, and matches the signed-in login; a mapped repository still being read or not readable is named, and none of its lists is read; no notification, search or account-wide issue list is read. No merge, review, comment, rerun, cancel, log, artifact or commit status endpoint is used.

## Code inspection

A repository's files are read at its pinned commit, named by its full ID: the whole tree in one reply (`git/trees/<sha>?recursive=1`), which keeps each entry's path, kind (file, folder, symbolic link by its mode `120000`, or submodule), blob ID and size, and is **partial** when GitHub says it cut the list; an entry with an empty, absolute, `.` or `..` path part, or a NUL, makes the tree **invalid**. A file's text is read through `readFile` at that commit, so its bytes must match GitHub's blob ID; bytes that hold a NUL or are not UTF-8 are kept as binary with only their size and blob ID. A leading byte order mark (U+FEFF) is kept in the text, so the view shows it like any other hidden character. Only plain paths (letters, digits, dots, dashes, underscores and slashes, no `.` or `..` part) are read; symbolic links, submodules and files GitHub gives as over 1 MB are not read. A commit's changes are read from the commit itself (`commits/<ref>`), by its ID or by a branch or tag name GitHub resolves now (a name not of the plain form is not sent): its ID, title, parents and changed files, each with its path, status, earlier path when renamed, lines added and removed and patch text, if GitHub gives one. Changes between two commits are read from `compare/<base>...<head>` between full IDs only, with GitHub's status, ahead and behind counts and common ancestor. A list of 300 changed files is **partial**, and so is a commit's list GitHub says goes on (a `rel="next"` link); a comparison's next page lists more commits, not more files, so it never makes its files partial. A reply with no list of changed files, or one with an entry not in the expected form, is **invalid**, never a change of no files; an explicit empty list is **empty**. Patches are split into lines with old and new line numbers; one not in the unified diff form is kept as plain lines. No blob, archive, raw, download, write or commit endpoint is used.

## Search

Search reads nothing: it looks only at the read results the page already holds in memory, and no endpoint is added for it. Its sources are the task rows of each plan whose table was read at the pinned commit (invalid rows left out), the repositories whose pin was read (name, description and topics, one result per pinned commit, so two projects pinning one repository at different commits give two results), the file paths of trees read at a project's pinned commit (folders left out), the files opened there (by their text; binary ones are not searched), and the pull requests in the activity feeds and Pull requests pages read on this visit (number, title and head, once per repository, number and head, so a pull request listed at two heads keeps both). With **Search inside tasks**, which is off by default, a task also matches by its other columns and by its brief, handover and cross-references when they were already read at that commit; a task file not read is not searched and is not read for it. The coverage says, for the tasks in scope, how many had file text searched, how many had every file read or found not there, how many have a file not read yet, and how many files could not be read by how the read ended (no access, failed, asked to wait, can't be read); a file whose read failed is never counted as searched. Every word typed must appear. Each result keeps its project, repository and commit (a pull request is GitHub's list as read, with the feed's read time when it has one), and the same ID in two projects, repositories or commits stays two results. At most 50 of each kind are shown with the full count. An excerpt is cut around the first word found and kept as plain text; `SB.textPieces` marks its hidden characters for the view. The words, the option and the scope (the current project, or every project) live in the page's state only, so Forget access, leaving the page, a restored page and a refused token drop them with everything else, and a refresh starts a new run that drops them too. Nothing is indexed or kept between searches beyond a lower-cased copy of each read text, held only as long as that read result.

## Repository web address

Pinning keeps the repository's web address from GitHub's own reply (`html_url`) when it is a plain `https` address ending in that repository's name, with no user name, password, query or fragment; otherwise none. Result-file links are built from it: `<web address>/blob/<commit>/<path>`, each path segment encoded; pull request links are `<web address>/pull/<number>`, commit links `<web address>/commit/<sha>`, issue links `<web address>/issues/<number>`, run links `<web address>/actions/runs/<id>`, release links `<web address>/releases/tag/<tag>` (the tag encoded), file links `<web address>/blob/<commit>/<path>`, comparison links `<web address>/compare/<base>...<head>`, and the clone address `<web address>.git`. A release asset links to its `browser_download_url` only when that is `https://github.com/<repository>/releases/download/…` with no user name, password, query or fragment; any other address is not kept. They open only when clicked, in a new tab with `rel="noopener noreferrer"`, and carry no token. No other web address is written in the code.

## Rendering repository text

`SB.renderText` puts text only in text nodes; it never parses HTML. A word becomes a link only if it is a plain `https` address without a user name or password; links open in a new tab with `rel="noopener noreferrer"`, and trailing punctuation stays outside. Nothing from a repository is loaded: no images, frames or scripts. Binary content is not shown and text over 100,000 characters is cut, each with a notice. Hostile fixtures are in `tests/fixtures/hostile-text.json`. File text and diffs are shown by the Files view as text nodes too, with no links at all, and `SB.textPieces` splits out each character that prints nothing or turns the text's direction so the view shows its code instead.

## Tests

`python3 -m unittest discover -s tests -v` also runs the browser-module tests in `tests/js/` with Node.js (`node --test`), against a mock of the GitHub API serving synthetic repositories. Node.js 20 or later is needed. The workspace checks (`tests/test_browser.py`, `tests/test_style.py`, `tests/test_demo.py`) are described in [WORKSPACE.md](WORKSPACE.md).
